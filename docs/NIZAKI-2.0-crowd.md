# 混雑予報(仮) — NIZAKI 2.0 の構想

作成: 2026-10-15。**構想の段階**(作り始めていない)。公開は 2026-11-01 0:00 の NIZAKI 2.0 と一緒(隠した状態で作る。版番号は上げない)。

## ひとことで
仮想の住民を、実際のダイヤの上で一日動かして、5日分の動きを平均すると、**駅 × 時間帯の混雑**と、**列車ごとの混雑**ができる。それを、アプリの混雑一覧・発車案内・経路検索で使い、**混雑と遅れをつなげる**。計算は事前にパソコンで済ませ、アプリは、できた JSON を読むだけ。

## 決まっていること(オーナーの判断)
- 見せる場所: 混雑一覧 + **発車案内 + 経路検索**。
- 仮想住民は、**各駅の乗降客数を元にした人数**にする。
- **混雑と遅れを、つなげる**。
- 参考にした実在サービスは、東京メトロの混雑統計(駅×時間帯の色の表。レベル1〜6)。**見た目の考え方だけ**を参考にして、色・言葉・名前は、そのままにしない。この機能の名前は、仮に「混雑予報」。

## しくみ(全体)
```
乗降客数の表(駅ごと) ─┐
ダイヤ(dia-2)        ─┼→ シミュレーター(Python) → 5日分 → 平均 → crowd-2/*.json → アプリ
遅れのルール(アプリと同じ)─┘
```
置き場所は `public/data/crowd-2/`。`isLaunched()` の内側だけ読む(ダイヤの `dia-2` と同じ隠し方)。

### 1. 仮想住民
- 駅ごとの**1日の乗降客数**を元に、「その駅から乗る人」の数を決める(乗降の半分が乗車、として計算)。
- 1人 = 実際の何人分、と決める(例: 1人=50人分)。人数が多すぎると計算が重いため、重みつきにする。
- 駅のタイプで、動き方を変える: 住宅型(朝に出て、夜に帰る)・業務型(朝に着いて、夕方に出る)・乗換のハブ・観光型(土休日の昼)。
- 平日と土休日で、別の動きにする。

### 2. 行き先と、乗る列車
- 行き先は、重力モデル(大きい駅ほど、近い駅ほど、選ばれやすい)で決める。
- 乗る列車は、「目的の時刻に着く、いちばん遅い列車」を中心に、少しばらつかせる。乗換も、ダイヤの上でたどる(アプリの経路検索と、同じ考え方)。
- 列車の定員は、車両数(特急・特別快速は10両、ほかは8両)× 1両あたりの定員で決める。

### 3. 5日分の記録
- 日ごとに、乱数と、遅れを変える。遅れは、アプリと同じルール(日付と列車番号で決まる)を、Python に移して使う。
- 列車 × 区間ごとに、乗っている人数を数え、**乗車率**にする。

### 4. 混雑レベル(6段階)
| レベル | 乗車率の目安 | 言葉(仮) |
|---|---|---|
| 1 | 〜50% | 座れる |
| 2 | 〜100% | ゆったり |
| 3 | 〜150% | やや混んでいる |
| 4 | 〜180% | 混んでいる |
| 5 | 〜200% | かなり混んでいる |
| 6 | 200%超 | 身動きが取れない |
(しきい値は、実際の混雑率の目安から。結果を見て、朝夕のハブ駅が赤くなるように、調整する。)

### 5. アプリに渡す JSON
- `station_slot_{平日|休日}.json`: 路線 × 方向 × 駅 × 30分枠(5:00〜翌1:00)のレベル(1バイト)。混雑一覧用。
- `train_{平日|休日}.json`: 列車番号 → 停車駅ごとの、その駅を出たあとのレベル。発車案内・経路検索用。
- 大きさは、合わせて 100KB 前後の見込み。

## アプリでの見せ方
- **混雑一覧**: 駅(縦)× 時間帯(横)の色分けの表。路線・方面・平日/休日の切り替え。セルを押すと、その駅のその時間帯の、詳しい内容。
- **発車案内**: 各列車に、混雑の印(例: 色つきの小さな帯)。いま遅れている列車は、レベルを1つ上げて見せる(遅れた列車に、人がたまるため)。
- **経路検索**: 結果に、混雑の印。並べ替えに**「空いている順」**を足す。
- いずれにも、「模擬(実在の混雑ではありません)」の注記を付ける。

## 混雑と遅れのつなぎ
1. **混雑 → 遅れ**: 自動の遅れの起きやすさを、その列車の混雑レベルで決める(今の「朝夕は2%→4%」のルールを、混雑に置き換える)。レベルが高い列車ほど、遅れやすい。朝夕のラッシュの遅れは、混雑から自然に生まれる形になる。
2. **遅れ → 混雑**: 遅れている列車は、見せるレベルを上げる。
3. 同じ列車は、同じ日なら、どの画面でも同じ遅れ(今の性質は、守る)。

## Three.js について
- 混雑の計算にも、一覧・印の表示にも、**要らない**(計算は Python、表示は今まで通りの画面)。
- 使うなら、「3Dで見る混雑ビュー」(駅が塔になって、混雑で色が変わる。仮想住民が点で動く)のような、**見せ場の画面**として。
- 気をつけること: 配信の大きさが増える(必要な画面を開いたときだけ読む形にする)/ 開きっぱなしで、GPUを使い続けない(画面を離れたら止める。以前、開いたままの3Dの画面で、GPUが95%になり、動きが重く感じた)/ 公開日までに間に合わせるなら、**あとの段階**。
- 提案: 公開日の主役は、2D の混雑一覧と、発車案内・経路検索。3D は、余裕があれば、公開後に追加する。

## 実装メモ(2026-10-15 シミュレーター完成)
- 置き場所: `tools/crowd-sim/`(`sim.py`・`stations.csv`=中堅級の乗降客数・`stations_large.csv`=大手級・`report.txt`)。実行は `python3 tools/crowd-sim/sim.py`(標準ライブラリだけ。約20秒)。結果は `public/data/crowd-2/` に書き出される。
- 乗降客数の表: 別のAIが作った概算(実在の駅の規模感から。実際のデータではない)。`stations.csv`(中堅級)を使い、`DEMAND`(既定 2.0)を掛ける。**列車の数に対して需要が小さすぎると、ほぼ一日中レベル1になる**ため、倍率で調整した(中堅級×2.0 = 大手級の0.8倍)。
- 仮想住民: 6万人。1人 = 約8.6人分(乗降客数に合わせて自動で決まる)。自宅・勤め先・遊び先・出発時刻のくせを持つ(通勤58% / 日中の外出26% / 夕方の外出16%)。駅ごとの乗降客数に合うよう、自宅と勤め先の選ばれやすさを、6回、補正する。
- 動かし方: 平日5日・土休日2日。日ごとに、出発時刻と、行くかどうかが揺れる。経路は、実際のダイヤの上で、乗換(150秒)を含めて、いちばん早く着く列車(有料特急は、15%の住民だけ)。
- 結果: `train_{wd|we}.json`(列車番号 → 区間ごとのレベル。1文字1区間)・`slot_{wd|we}.json`(路線 → 方向 → 駅 → 30分枠×40=5:00〜翌1:00のレベル。0は列車なし)。合わせて約100KB。
- いまの癖(要確認): 埼千環状線の新宿まわりが、夕方に長くレベル6になる(新宿・池袋の乗降客数が大きく、列車の数が少ない)。神埼線は、ほぼ、レベル1〜2。調整は、需要の倍率・駅の格ごとの住む人/働く人の比率・混雑レベルのしきい値で行う。

## 経路検索の混雑(2026-10-15)
- 各候補に、乗っている区間のいちばん混むところの混雑(色つきの短い言葉)。乗換があれば、列車ごとにも出る。詳細には「混雑の目安」。3分以上遅れている列車は、1段階高く見せる。
- 絞り込みに「結果の並べ方: 早く着く順 / 空いている順」を追加。空いている順は、早く着く候補を8件探し、いちばん早く着く便から45分以内のものを、「乗っている時間で重みをつけた混雑の平均」の低い順(同じなら早く着く順)に、3件出す。
- シミュレーターの改良(同じ日): ①出発時刻のまとめを5分から1分に。②住民に5種類の「好み」を付け、列車ごとに±3分の感じ方のずれを持たせて、最速の列車だけに、全員が乗らないようにした。③同じ駅を出る前後の列車と、混雑をならした(自分の値5割 + 前後の列車の平均5割。幅は5分)。実行は約200秒。
